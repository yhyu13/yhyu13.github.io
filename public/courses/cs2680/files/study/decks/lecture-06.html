Agents design III: agent memory and reliability

The definition

Memory is persistent state beyond the context window

Context window

Temporary working state.

  • Dies with the session
  • Re-sent on every step

Memory store

Persistent state across interactions.

  • Loaded at session start
  • Has its own lifecycle, cost and failure modes
Six policy questions, each with a named decision: keeping (WRITE OR SKIP), format (ENCODE / ORGANIZE), need (RETRIEVE), lesson (REFLECT / GENERALIZE), valid (KEEP / UPDATE / DELETE), backend (STORE). "Who owns the memory?" appears to be the lead-in answered on p15, not one of the six.

The first question

Keeping: recall against noise

Write every interaction

High recall, noisy.

Write selectively

High precision, through one of four routes.

  • Explicit user request
  • Deterministic rules (heuristics)
  • A small classifier
  • Periodic LLM review
The whole memory half is a set of policy decisions, not a database. Every stage - observe, select, encode, store, retrieve, reflect, forget - is a decision the designer has to make.

Usage policy

Three ways to decide when to use memory

Automatic

Every turn: search, LLM, add. Predictable, but adds latency and irrelevant context.

Runtime-controlled

if memory_needed: search(); if memorable: add(). Selective, but needs rules or a classifier.

Model-controlled

search_memory(), add_memory(), update_memory(), forget_memory(). Demand-driven, but may miss useful reads or writes.

The read and write policies being separable is the practical point: an agent can be told when to look without being told when to write.

The fourth question

Retrieval needs more than semantic relevance

Semantic match

Is it about the same thing?

Scope

Same user, project, entity or task.

Importance

The cost of missing it, or of including it.

Validity

Is it true for this task at this time?

Provenance

Source, confidence, evidence.

Five retrieval signals. This is the point where the evaluation note's "memory recall and query latency" dimension gets its operational meaning.

The fifth question

Lesson: consolidation and forgetting

Generalise

Repeated questions about vLLM, SGLang, TRT-LLM and LLM scheduling become the hypothesis "frequent interest in LLM inference systems", at medium confidence.

  • Consolidate every N events or on context fill
  • Consolidate when facts conflict or repeat
  • Or consolidate in a background job

Forget

Forgetting is a first-class operation, not a missing feature.

  • Controls: mark invalid, erase permanently, expire after a TTL, tier and evict from active memory
  • Reasons: stale information; incorrect or conflicting information; privacy and security; storage and retrieval cost
This is the second "students get this wrong" point: a memory without a valid time silently overrides newer information.

The sixth question

Valid time and provenance are part of the data model

The same fact, twice

  • April 2026: the project serves models with vLLM - superseded
  • June 2026: the project serves models with SGLang - current

The source

  • Episode 28 is the source of the fact
  • The relation is written Project -> SERVES_WITH -> SGLang
If you cannot say when a fact stopped being true and where it came from, you cannot expire it, and you will eventually act on a stale fact.

Ownership

Who owns the memory?

Agent-owned memory

Files in the harness: CLAUDE.md, an agent scratchpad, task notes, persisted to disk by the harness.

A dedicated memory system the agent calls

Mem0 - fact-centric; messages scoped by user, agent and run; vector search with filters, plus optional graph memory.

  • Graphiti - temporal knowledge graph over episodes; hybrid semantic, keyword and graph search; facts valid from a date
  • supermemory - maintains a user profile alongside memory and document, with conversations linked to source and time
The three named systems differ in granularity: fact-centric, temporal graph, and profile-centric. That choice is the difference between a lookup table and a model of the user.

How memory is measured

Four evaluation axes, and four benchmarks

AxisMetrics
Writes and updatePrecision, recall, stale-memory rate
RetrievalPrecision, recall
SystemLatency, token overhead, store growth

Named benchmarks: LoCoMo (ACL 2024) - 1,540 questions over 10 long dialogues; LongMemEval (ICLR 2025) - 500 questions over 5 memory abilities; BEAM (ICLR 2026) - 2,000 questions, up to 10M tokens; and LoCoMo-Refined.

These are the benchmarks the Lecture 7 component-level evaluation is built to measure. Memory is the component that usually gets measured first, because it is the easiest to isolate.

Reliability, first as arithmetic

Errors compound

With each step succeeding independently with probability 0.95, a long run is not likely to be clean.

A 50-step run finishes error-free only about 1 in 13 times. The deck notes that error propagation makes real runs worse than this model.

This is the cheapest slide in the course and the most persuasive: bound the run, or accept the compounding.

Reliability, then as attribution

Five fault origins

LayerFailure modesExample from the deck
User / task specSpecification failure: ambiguous goal, proxy objective, unstated constraint, no definition of done, conflicting goals5 modes
Agent harnessHarness failure: context truncation, memory error, state corruption, control loop error, blocking fan-out"200 steps, no progress"
LLMModel failure: hallucination, instruction violation, faulty reasoning, reasoning-action mismatch, unverified success, long-horizon degradation"requests.fetch() exists"; "undid its own fix from step 12"
Tool layerTool failure: truncated output, silent failure, ambiguous schema, flaky call, misleading errorThe first 100 lines of a log missed an error on line 4,000; a date with no time zone scheduled a job 8 hours off; retried with sudo
EnvironmentEnvironment failure: stale state, version mismatch, random failure, rate limitPython 3.8, not 3.12; HTTP 429 after 50 calls; leap year; redesigned checkout page

Each layer carries a table of concrete failure modes paired with a fix. The counts: 5 specification failures, 5 harness failures, 6 model failures, 5 tool failures, 4 environment failures.

Locate the fault layer before fixing anything. Most "the model is bad" reports are really layer two or layer five.
