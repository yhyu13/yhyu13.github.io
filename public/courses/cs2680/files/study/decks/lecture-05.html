Agents design II: multi-agent architecture, coordination, and communication

When to split work across agents, which topologies exist, how they talk - and what each one costs.

The lecture opens by saying multi-agent has decades of research history which it will not get into, and closes by asking whether it is really necessary. Multi-agent is presented as a cost, not a default.

Why split at all

Four stated reasons

Specialization

Different models, prompts and tools.

Isolation

Different privileges per agent.

Parallelism

Independent subtasks run concurrently.

Context management

Do not give every agent the whole trajectory.

If none of the four apply, the closing question - "is multi-agent really necessary?" - usually answers itself.

The vocabulary

Three graphs describe any multi-agent system

Every architecture slide in the deck ends with the same three-field tag line: Task, Control, Comms.

Control graph

Who coordinates: one supervisor, a hierarchy, or nobody - possibly changing at runtime via handoff

→

Communication graph

How they communicate: direct messages, broadcast, or a shared workspace

→

Task graph

How work is decomposed: up front by a planner, by bidding, or emergently from local rules

Students are taught to read any multi-agent diagram with this vocabulary. The three graphs are the spine of the lecture.

The deck maxim for the pipeline case: "one retry edge beats one more agent". Every architecture ships with a named weakness - that pairing is the point of the slide.

Three topologies in detail

Centralized, mostly

Supervisor-worker

Best when subtasks are independent and parallelizable. The supervisor plans, delegates and integrates; workers see only their subtask.

Hierarchical

Fits tasks that already decompose hierarchically - storage, query engine, testing. The open question is where decomposition happens and how much context crosses each boundary.

Pipeline / DAG

The cheapest topology to debug, because errors localise to a stage. But there is no path backwards.

The hybrid example is the one to quote when students ask what to actually build.

Shared state

Blackboard architecture

What it gives you

  • Agents coordinate through shared state instead of direct messages
  • The workspace may be a database, vector store, filesystem, Git repo or task graph
  • Agents can join or leave without rewiring
  • Shared state is durable and inspectable

What it costs

  • Consistency
  • Concurrency control
  • Provenance
  • Versioning
  • Garbage collection
The blackboard is the storage half of the memory stack, and it reappears in Lecture 8 as a provider inside a modular harness.

Markets and committees

Two ways to resolve without a planner

Market / auction

Agents bid for announced tasks on capability, cost and latency, so work lands on the cheapest capable agent with no central planner.

  • Worked example: A100 node $0.20, ETA 3s; T4 node $0.05, ETA 10s; H100 node $0.40, ETA 1s
  • Rule: cheapest bid under 5s wins - the job goes to the A100 node

Committee / debate

Agents propose and discuss, then a judge or vote resolves.

  • Failure mode: agreement without independence - same model and context means the same blind spot
  • Market failure mode: bids are self-reported, so an agent can win by overstating what it can do
Both are named as "this is the thing students get wrong": committees converge on the wrong answer for the same reason, and markets reward dishonest bids.

The extremes

Swarm, dynamic topology, and the hybrid that is real

Swarm

No permanent coordinator, so it needs protocols for discovery, addressing, synchronization, termination and trust. Communication complexity is O(n^2) and it is rarely used in products.

Dynamic topology

Adds, removes or rewires agents while the task runs - a support bot adding billing and log agents only on escalation. Capacity scales with difficulty, but failures are hard to reproduce.

The hybrid

Planner agent + Coder/Researcher/Tester/Reviewer + Shared Git + dynamic task DAG. It combines hierarchy, shared memory, pipeline and re-planning.

A dense mesh is rarely the best default: more communication can increase context pressure without increasing useful information.

Decomposition

Axes, specs, and modes

Six axes to split on

Example: a 200-file PR split by data (files), then by expertise (security, perf).

  • Data
  • Expertise

  • Hypothesis
  • Tool

Eight fields a sub-task spec needs

  • Objective
  • Inputs and relevant context
  • Boundaries and exclusions
  • Available tools and permissions
  • Expected output schema
  • Completion test
  • Budget and deadline
  • Dependencies
Decomposition needs spawning limits, budgets, depth limits and termination conditions, or delegation explodes. That is the warning the slide carries.

Granularity

Parallelism has to pay for itself

QuantityValue
T_multi ~= T_planning + T_critical_path + T_communication + T_mergeParallelization only helps when the saved sequential work exceeds planning, communication and integration cost
Batching example20 one-line lookups batched into 4 subtasks

Named decomposition failures: 01 Overlap, 02 Gap, 03 Hidden dependency, 04 Unmergeable outputs, 05 Lost global context, 06 Straggler. A gap example: "2020-2023" plus "2025-2026" skips 2024. A straggler example: six agents finish in 20s, 25s, 4 min - and one straggler sets the total.

The straggler example is the one that connects to Lecture 3: the slowest subtask sets the total time, which is why subagent parallelism buys elapsed time and not answer quality.

Communication

A worked message: task_id "T17", type "result", status "complete", confidence 0.82, evidence ["log:2391", "commit:X"], artifact "analysis/T17.json".

Messages should carry semantics: natural language for content, structured protocol for coordination, so the runtime can route, retry and stop without asking an LLM what the message meant.

Control messages

Nine runtime operations, and the failure they must survive

The nine operations

  • DELEGATE, QUERY, REPORT, HANDOFF, UPDATE, CANCEL, ACK, ERROR, COMPLETE
  • A worked control message: id "msg-381", task_id "t-17", from "planner", to "researcher", type "DELEGATE"

The failure scenario

The task is to "purchase 8 GPU instances". The network times out and no reply comes back.

  • At-most-once, at-least-once - and "is exactly-once even available here?"
  • The answer is an idempotency key on the task_id
This is taught as a distributed-systems problem, not an NLP problem. The timeout asks about exactly-once semantics and compensation, and structured control fields are what let the runtime act on its own.

Inherited problems

What multi-agent inherits, and what black-box LLMs add

From distributed systems

  • Partial failure
  • Concurrency and non-determinism
  • Consistency
  • No global clock
  • Unreliable network
  • Debugging and observability

From the LLM layer

  • Scheduling, state management and resource allocation on top
  • Information loss
  • Context pollution
  • Stale information
  • Conflicting beliefs
  • Lost ownership and communication loops

A2A

The agent-to-agent protocol

The shape

  • A machine-readable agent card at a well-known path - for example GET /.well-known/agent-card.json
  • Three abstractions: Message, Task, Artifact
  • A stateful task lifecycle with eight states: Submitted, Working, Input required, Auth required, Completed, Failed, Rejected, Canceled
  • Three tracking modes: polling for short jobs, streaming for interactive, push notification for hours-long jobs

Worked example

  • Task: "Analyze whether company X should move its inference stack to GPUs Y."
  • Peers: Research Agent, Finance Agent, Search Agent, Coding Agent
  • Agent card: "Travel Agent", skill id "book-flight", capabilities streaming: true
  • Task-42 moves working to completed; a follow-up "Which date?" is answered "Oct 3"
The memorable claim: one A2A remote agent may itself call twenty MCP servers. A2A is service-to-service RPC; MCP is device-to-API.

MCP vs A2A

Two different boundaries

MCPA2A
Primary abstractionTools, resources, promptsMessage, Task, Artifact

DiscoveryThe host, not the model, decides what is exposedAgent card at a well-known path
Unit of workA capability callA task with a stateful lifecycle
Internal stateThe host holds itThe agent holds it

MCP is the agent-to-capability boundary; A2A is the agent-to-agent boundary. The two compose: an A2A remote agent may itself call twenty MCP servers.

This is the direct ancestor of the Lecture 8 harness comparison: MCP becomes one of the modular harness's providers, and the microkernel is the "A2A with services" shape.

Closing

Four design principles

  • 1. Is multi-agent really necessary?

  • 2. Decide the topology.

  • 3. Identify the information-loss points.

    A supervisor aggregating four workers' results is where detail drops.

  • 4. Identify the failure-containment boundaries.

    "A dense mesh is rarely the best default. More communication can increase context pressure without increasing useful information."
