The category shift

AI/ML asks one question, AI Systems asks another

AI/ML

"What model should we use?"

  • Optimizes accuracy
  • Optimizes capability
→

AI Systems

"How do we train and serve it at scale?"

  • Optimizes GPU utilization
  • Optimizes resource waste
  • Optimizes downtime
  • Optimizes carbon
The deck contrasts the two questions and the four optimization targets under each. This is the framing the MaDSys group brings: efficiency, reliability, performance, sustainability.

Compute differences

An agentic workload is not a transformer workload

Heterogeneous work split

CPU lane: tokenization, kernel launch, data movement, tool calls. GPU lane: matmul.

Distinct phases

Prefill is compute-bound; decode is memory-bandwidth-bound.

Output-length-dependent runtime

Execution time depends on how long the answer is, which complicates scheduling.

Why this matters for a course about agents: the tool-call phase runs on the CPU while the model phase runs on the GPU, and the two cannot be batched the same way.

Non-determinism

The same request does not always give the same answer

Where it comes from

  • Runtime: warp and block scheduling, memory ordering, async streams, batch size
  • Software: fused multiply-add, autotuning, subnormals
  • Hardware: CUDA vs tensor core, Hopper FP8 vs Blackwell micro-scaling tiles

Why it matters

Floating-point addition is not associative, so a shift in the 7th decimal of a matmul can flip the next token.

  • Approximate computing is acceptable
  • The consequence is that single runs are not measurements
Do not let students treat a single run as a result. This is the same argument the evaluation lecture later makes about non-determinism making single-run scores noise rather than signal.

The remaining differences

State, communication, churn, reliability and power

DimensionWhat the deck records
StateModel weights GBs to TBs; KV-cache 10s-100s KB per token; prefix cache reuses KV across requests
CommunicationPipeline, tensor, expert and context parallelism; NCCL, UCCL; NVLink, Ethernet/InfiniBand, RDMA
ChurnMHA, GQA, MLA, NSA, linear attention; workloads: multi-turn chat, problem solving, RAG, agents
Reliability9% AFR, 50,000hr MTBF; one GPU fails every 3 hours in a 16K-GPU cluster
PowerCPU 100-300W, GPU 700-1000W, 4-8 GPUs per server; server power 800W to 6,000W, an 8x increase
The lecture walks these as structural differences, not incidental ones. The 9% AFR figure and the 50,000hr MTBF set the bar that a serving system has to clear.

The agent

A new kind of programmable computer

An agent is an autonomous software system that uses an AI model to reason about a goal, use external tools, and execute multi-step actions until the task is finished.

The computer analogy: context window as RAM, tools as peripherals, agent harness as OS, agent as application - a different programming model and a different failure model.

The five steps are printed on the deck as 1 plan, 2 act, 3 observe, 4 adapt, 5 deliver. The computer analogy is what makes the systems framing work: if the harness is the OS, then everything the OS is responsible for is on the table.

Why agents

LLMs are strange computers

Superhuman at

  • Recalling factual knowledge
  • Language
  • Pattern matching
  • Generating code
  • Operating across many domains

Surprisingly weak at

  • Persistent memory
  • Reliably understanding context
  • Avoiding hallucinations
  • Knowing what they do not know
  • Security and adversarial input
The framing the lecture uses twice: LLMs are superhuman and incompetent at the same time. The weaknesses on the right are exactly the problems the harness has to solve.

Serving

Agent serving replaces request-inference-response

Classic serving

  • Request
  • Inference
  • Response
→

Agent serving

  • Infer
  • Tool
  • Infer
  • Tool
  • Retrieval
  • Infer

The critical path now spans GPU, CPU, storage, network and external services.

This is the structural difference the whole course is built on. Once a tool call sits between two inference calls, no single model call owns the latency budget.

The objective

Throughput is the wrong objective for an agent

Useful but insufficient

  • TTFT / TPOT
  • Tool-call latency
  • GPU utilization
→

Actually optimized

  • Task success / accuracy
  • End-to-end latency
  • Tokens per task
  • Dollars per successful task
  • Energy per successful task

The objective is to maximize task success subject to latency, cost, resources, reliability and security. More tokens per second can still mean a slower, costlier agent.

This is the scoreboard the rest of the course tries to move. Everything in Part II - cost decomposition, Pareto ranking, the leaderboard - is an attempt to move one of the numbers on the right.

Scope

What this course does not cover

Explicitly out of scope

  • Training and the data pipeline
  • Checkpoints
  • Pre-training, fine-tuning, post-training, RL rollout
  • Cluster management
  • Model architecture design and communication
  • Power and energy; new hardware design

In scope

  • Inference and serving
  • The agent harness
  • Context and memory management
  • Scheduling, caching, routing and batching
  • Observability and fault tolerance
The exclusions are printed on the deck. It is worth saying out loud that Part II is where the serving material lands.

The course questions

Nine questions the course is built to answer

Printed on the deck as the questions the course will work through.

  • Serving and scheduling

    • Why does batching improve throughput but hurt agent latency?
    • When should we use a larger model?
    • Where should KV and prefix state live?
    • Can tool calls overlap with inference?

  • Agents and operations

    • When should we spawn a subagent?
    • How do we route across heterogeneous GPUs and models?
    • How do we recover a 30-minute agent?
    • How do we optimize dollars per successful task?
Nine questions. Every later lecture answers one or two of them. Keep this slide in mind when the course returns to cost, evaluation and serving.
