Agent design I: context management and tool design

The harness from first principles: the loop, the tools, the context ladder - and the claim that changing only the harness doubles accuracy.

This is the first lecture in the design half of the course. Everything here is a design decision a student will have to make in Assignment 2 and defend in the writeup.

The loop

ReAct: Thought, Action, Observation

The three parts

  • Thought - what do I know, what is missing, what next
  • Action - emit a structured call the environment can run
  • Observation - the environment answers with facts

Two broken variants

  • Reason-only fails: nothing checks the reasoning, and small errors compound into confident hallucination
  • Act-only fails: tool calls with no plan make the model repeat themselves
The same loop Lecture 2 demonstrated with Claude Code, now written as code. Point out the two failure modes: they are the two things students tend to build.

The reference implementation

A message-list loop, and the three jobs of a harness designer

The loop

  • System and user messages, then for step in range(MAX_STEPS) call the model with tools
  • Append the response; return the final answer if present
  • Otherwise validate arguments, execute the tool, and append a role "tool" message with tool_call_id and content
  • Exceeding the step limit raises RuntimeError("Agent exceeded its step limit")

A harness designer has three jobs

  • Assemble the context
  • Validate the request, check permission and run it
  • Optionally process the result and manage context
"An agent is a model plus a loop" and "tools set capability; guardrails keep it safe". The three jobs map directly onto the three components of a coding agent.

Finding code

Four ways to find code

ApproachStrengthCost
Glob and grepAlways reflects the live repoBurning turns and context; misses paraphrase
Semantic / structural searchFast at query timeBuilding and re-syncing the index
Extrinsic signalsThe highest-precision signal when debugging - stack traces, failing tests, git historyUseful only when such a signal exists
Language server (LSP)Resolves imports, overloads and renames that grep only guesses atA live server per language, and a slow cold start

The comparison rule from the deck: "In practice - start with grep; reach for an index or LSP when names run out." Examples on the slides: grep -rn "timeout" src/ gives 37 hits in 12 files; a textDocument/references query returns 42 call sites across 7 files; Aider's repo map is the structural-search example.

The point for the students: a semantic index is a build cost, and an LSP is a runtime cost. Both are worth it only when the names run out.

Changing code

Four edit strategies

StrategyStrengthFailure mode
Whole-file rewriteNo patch syntax to get wrongOutput scales with file size; untouched code can drift
Unified diff / patchCompact and reviewable in the format humans and CI already useHunks fail when line numbers or context drift
Search and replaceOutput proportional to the changeFails on ambiguous, stale or whitespace-off anchors
Structured / AST editImmune to formatting; cannot produce invalid syntaxPer-language tooling and a limited set of expressible edits

Examples on the slides: a whole-file rewrite reads client.ts (120 lines) into context and changes 4 lines; a unified diff is 6 lines in two hunks applied with git apply patch.diff; search and replace turns retries = 3 into retries = 5; an AST edit adds a parameter with a 5s timeout default and rewrites the signature and all 18 callers, valid by construction.

The AST and LSP background links are https://pierce.dev/notes/how-language-servers-work and the "Abstract syntax trees" video. The four-row comparison is the summary table the deck prints.

The most powerful tool

Shell execution

Why it is powerful

  • Composition - one call can chain, filter, loop and retry
  • Reach - filesystem, network, package managers, installed binaries
  • Persistence - files and processes outlive the call
  • Blast radius - whatever the shell can do, the agent can do

Five design questions

  • Failure signal
  • Output
  • Duration
  • Budgets - when to stop retrying and hand back
  • Isolation - where the code runs and what it can reach
These five questions are the agenda for the tool-design part of the project: the blast-radius question is the one that decides whether the shell is allowed at all.

The rest of the tool set

Five more tools, five design rules

Five more commonly used tools

  • Browser and visual feedback
  • Memory and notes - write findings to a file so plans survive compaction
  • Asking the user - one cheap question beats a confident wrong patch
  • Subagents and delegation
  • Web search and fetch

Five best practices

  • Few orthogonal tools - overlapping tools make the model dither
  • Purpose-built rather than generic - search_orders(customer_id) beats a raw run_sql tool
  • Token-cheap output: truncate, paginate, summarize. Tool design is context design
  • Errors that teach - return the fix hint, not just "invalid argument"
  • Idempotent by default
The "token-cheap output" line is the hinge into the context section: a tool's output is context, so tool design and context design are the same problem.

Prompting

Eight techniques, four rules

Eight techniques

  • Zero-shot
  • Few-shot
  • Role and persona
  • Chain-of-thought
  • Tree-of-thoughts
  • Self-consistency
  • Prompt chaining
  • Meta prompting

Four prompt-design rules

  • Instruction, delimiter, data - in that order
  • Start simple then iterate
  • Partition into sections
  • Be specific and concise; split big tasks into subtasks
Chain-of-thought is shown as 3 features/week for 4 weeks then 5/week for 2 weeks, giving 12, 10 and ANSWER: 22. Tree-of-thoughts scores 3 ways to cut checkout latency from 1 to 5, expands C then B and prunes A.
"
The delicate art and science of filling the context window with just the right information for the next step.

Andrej Karpathy - cited in Lecture 4, PDF page 41

Context is a finite resource on three axes: cost (every step re-sends the whole window), latency (bigger prompts take longer to prefill and decode) and attention (recall fades as the window fills, and the middle gets missed). More context is not better answers.

The ladder

Four escalating stages of context management

The stages run from preventive and lossless to lossy and irreversible.

1

Admission

Targeted retrieval, tool output shaping, truncation only when shaping cannot, isolation to a subagent.

2

Offloading

Progressive tool definition, tool search, tool output offload returning a handle, externalised task list, persistent memory.

3

Transformation

Deduplication, observation masking of tool results older than N steps, sliding window.

4

Compaction

Rolling summary, or full summary at the limit, reserving headroom, preserving the system prefix, re-injecting critical facts, persisting key facts outside the window via auto memory.

The order matters, and the lecture says so: admission, offloading, transformation, then compaction. Compaction is the one that is lossy and irreversible, so it is the last resort.

The ladder, measured

Three savings, one per stage

StageBeforeAfterResult
AdmissionRaw DOM, 48,000 tokensPrices and headings only, 900 tokens98% smaller, same answer
Offloading60 schemas resident, 42,000 tokensIndex plus 3 schemas, 3,100 tokens93% smaller, all 60 reachable
TransformationEvery result kept, 96,000 tokensNewest state kept, 24,000 tokens75% smaller, nothing summarized
Notice what each stage refuses to do: admission shapes rather than truncates, offloading keeps everything reachable, transformation summarises nothing. The savings come from structure, not from dropping information.

How context fails

Five failure modes - and the fix follows from the name

Poisoning

A hallucination enters the window and is later cited as fact.

Distraction

History grows until the agent imitates its own past actions.

Confusion

Irrelevant tools and documents steer the answer off course.

Clash

New information contradicts old; both stay unresolved.

Drift

The real goal is buried and swapped for a nearby subgoal.

The diagnostic skill here is the one the project rubric rewards: break the 60-second result into the 40 seconds of tool calls and see which of the five you are in.

The thesis

2x

accuracy, from changing only the harness

Model capability sets the ceiling; the harness determines realized performance. "Some apparent 'model failures' are actually context- and control-loop failures."

The evidence on the next slide. This is the single number the whole lecture is built to defend.

The four harness changes listed on the slide: old tool outputs compacted; recent observations kept visible; repetition and stalls detected; interventions when stuck. Source: Lewis, S., "Same Model, Different Harness: Different Coding-Agent Results" (arXiv:2608.26218, 2026).

Same model, same tools, same tasks - only the harness changes. This is the bridge to Lecture 3's "same model, different workflow" and to Assignment 3, where the harness is the deliverable.

Beyond ReAct

Three other loop shapes

Reflexion

Loops after a failure: Attempt, Evaluate, Critique, Retry.

Plan-and-execute

Loops on deviation: Plan, Execute steps, Re-plan.

Tree search

No loop - one pass, wide: State, Branch A/B/C, Keep best.
