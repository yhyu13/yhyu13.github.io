# Part I Digest - CS2680 (slides 1-4)

Part I of CS2680 (Modern AI Systems: Agents and System Optimizations, Harvard SEAS, Fall 2026, instructor Juncheng Yang) walks one agentic system from top to bottom. Lecture 1 frames the course as a systems course and names the gap between "AI/ML" and "AI Systems"; Lectures 2-3 take the user-facing view of Claude Code as the concrete artifact, covering the agentic loop, memory, tools, the four extension mechanisms, and how to fan out to many agents; Lecture 4 flips to the inside of the harness, covering the ReAct loop, tool design, prompt/context engineering, and the claim that harness design alone moves benchmark accuracy. The through-line is that a model sets the ceiling while the harness (loop + tools + context + memory + orchestration) determines realized performance, and every property of an agentic workload maps to a systems problem.

## Lecture 1 - Overview
- **Source PDF**: `course/site/slides/1_intro.pdf` (slides: 50 pages, extracted from that file)

### Concepts
- A graduate-level computer systems course on agentic AI systems, expecting one prior graduate-level systems course (OS, networking, databases, architecture) plus real systems experience; its shape is Foundations (first few classes) and Systems for LLMs & agents (the majority) - GPU programming and kernels, batching/scheduling/memory management, load balancing and routing, KV-cache and prefix-cache, agent serving systems. (p9, p10)
- Five assignments: build a web UI for Claude Code, build a simple coding agent, optimize your coding agent, serve your agent, optimize the full stack; assignments 3 and 5 are leaderboard-scored, and the project is either a tool you will actually use or a research project. (p11, p12, p13)
- Two ladders of agent adoption: AI use levels (1 Chat, 2 Coding agent with MCP/Skills/Plugins/subagent/parallel agent, 3 Customized agent) and Agentic Coding Levels (0 No AI through 5 Parallel agents). (p25, p26)
- AI systems means many moving parts (scheduling and orchestration, state management, communication, caching, fault-tolerance, security, observability); AI/ML asks "what model should we use" and optimizes accuracy and capability, while AI Systems asks "how do we train and serve it at scale" and optimizes GPU utilization, resource waste, downtime and carbon. (p28)
- Compute differences: heterogeneous work split (CPU for tokenization, kernel launch, data movement, tool calls; GPU for matmul), distinct phases (prefill compute-bound, decode memory-bandwidth-bound), and output-length-dependent execution time that complicates scheduling. (p30)
- Non-determinism: floating-point addition is not associative and a 7th-decimal shift in a matmul can flip the next token, arising from runtime (warp/block scheduling, memory ordering, async streams, batch size), software (fused multiply-add, autotuning, subnormals) and hardware (CUDA vs tensor core, Hopper FP8 vs Blackwell micro-scaling tiles); approximate computing is acceptable. (p31)
- The remaining differences are equally structural: state (weights GBs to TBs, KV-cache 10s-100s KB per token, prefix cache), communication (pipeline/tensor/expert/context parallelism, NCCL, UCCL, NVLink, Ethernet/InfiniBand, RDMA), churn (MHA, GQA, MLA, NSA, linear attention; chat, problem solving, RAG, agents) and reliability/power (9% AFR, 50,000hr MTBF; CPU 100-300W vs GPU 700-1000W). (p32, p33, p34)
- An agent is an autonomous software system that uses an AI model to reason about a goal, use external tools, and execute multi-step actions until the task is finished, running plan -> act -> observe -> adapt -> deliver; an LLM is thus a new kind of programmable computer (context window as RAM, tools as peripherals, agent harness as OS, agent as application) with a different programming model and failure model. (p36, p38)
- Why agents are needed: LLMs are "strange computers" - superhuman at recalling factual knowledge, language, pattern matching, generating code and operating across many domains, yet surprisingly weak at persistent memory, reliably understanding context, avoiding hallucinations, knowing what they do not know, and security/adversarial input. (p37)
- Agent serving replaces request-inference-response with a chain of infer, tool, infer, tool, retrieval, infer, whose critical path spans GPU, CPU, storage, network and external services; the stack runs Application -> Agent/Harness -> Model -> Serving System -> Runtime/Kernels -> Hardware with an External Environment, and the objective is to maximize task success subject to latency, cost, resources, reliability and security - throughput is the wrong objective. (p39, p40, p41)
- Every agentic workload property names a systems problem: long trajectories -> state and context management; repeated prefixes -> prefix caching; tool dependencies -> dependency-aware scheduling; variable tool latency -> asynchronous execution; multiple agents -> orchestration and communication; huge context -> memory hierarchy and retrieval; branching reasoning -> speculative execution; different models -> routing; external side effects -> security and isolation; long-running tasks -> checkpointing and fault tolerance. (p42)
- Observability is first-class - the distributed trace becomes a nested trajectory (session, turn, agent step, model request, tool call, tool result, subagent) because "You cannot optimize what you cannot observe" - and the course's scope explicitly excludes training, data pipeline, checkpoint, pre-training/fine-tuning/post-training/RL rollout, cluster management, model architecture design, communication, power and energy, and new hardware design. (p43, p45)

## Lecture 2 - Agent From a User's Perspective I: How Claude Code Works
- **Source PDF**: `course/site/slides/2_agent_use_1.pdf` (slides: 53 pages, extracted from that file)

### Concepts
- The agentic loop: 1 gather context (prompt, files, tool results), 2 generate action (run a tool: bash, read, edit), 3 run tool (tests, output, re-read state), and repeat - every step is conditioned on what the last one returned, so one user prompt is many model calls and many tool executions rather than a single request. (p6)
- Context exists before the first keystroke and is already 10+k tokens: SYSTEM (Claude Code instructions), PROJECT (environment), MEMORY (persistent project/user notes/CLAUDE.md), TOOLS (Read, Edit, Bash, Glob, Grep, Web, Agent), SKILLS/MCP (names and descriptions only) and USER (the request); skill and MCP entries start as names only and load in full when the agent reaches for them. (p7)
- The model proposes and the harness executes: the model emits a request such as Bash("pytest"), the Claude Code harness resolves it, checks permissions and executes, and the tool_result goes back into the model's context; the repository itself never leaves disk, because Claude pulls slices of it on demand. One user turn therefore expands into an alternating chain - U prompt -> M1 inference -> T1 tool -> M2 inference -> T2 tool -> Mn inference -> A answer - and every request is conditioned on the previous inference and the previous tool result. (p8, p9, p10)
- Permissions sit between intent and execution: a tool request is a proposal needing approval, with modes Manual, Accept Edits, Bypass permission and Auto (a small model checks it), producing allowed, ask or denied. (p11)
- Context grows with every step and is then compacted by summarizing the old trajectory and re-injecting CLAUDE.md and memory; typical context size is 1M tokens, and context is not free because prefix-cache reads account for most of the cost. (p12)
- Agents are stateless between runs - every session starts from zero - so "memory" in practice is just files loaded at session startup: context is working memory that dies with the session, persistent memory survives and is reloaded. Every memory creation is a decision about what gets re-read forever, every permanent token is rent paid at the start of every session, and stale memory is worse than none because it actively misleads; treat memory like code and keep it in version control. (p16, p26)
- Two systems carry knowledge forward, both loading at the start of every session: CLAUDE.md files (written by you; instructions and rules; project, user or org scope) and auto memory (written by Claude; learnings and patterns; per repository, shared across worktrees). (p18, p19)
- CLAUDE.md lives broadest-scope-first, with the closest file read last: managed policy (.../ClaudeCode/CLAUDE.md, org-wide, cannot be excluded), user instructions (~/.claude/CLAUDE.md), project instructions (./CLAUDE.md or ./.claude/CLAUDE.md) and local instructions (./CLAUDE.local.md, personal and gitignored). It should stay under 200 lines per file and hold commands, hard constraints and facts the agent cannot cheaply infer - not what the model already knows, linter-enforced style, prose, changelogs or secrets - and long files should split into .claude/rules/ with a `paths:` frontmatter so each rule loads only when matching files are touched. (p20, p21, p22)
- Auto memory lives in ~/.claude/projects/<project>/memory/ with MEMORY.md as the index plus per-topic files, a type field tagging every file, and it is on by default (disable with /memory); retrieval loads the index always and reads topic files only when relevant, and four commands control it - /memory, /context, /init, /doctor. (p23, p24, p25)
- The core tool set: Read (open a file, inspect state - the most used tool), Search (grep and glob), Fetch (pull a page or doc - brings untrusted text inside), Edit/Write (change files - the first tool with consequences), Shell (build, test, git - the whole machine unless sandboxed), Delegate (spawn a subagent - a tool that returns a summary). (p28)
- Four extension mechanisms that are not interchangeable: Skill = how the agent should perform a task, MCP = which external data and actions it can reach, Hook = what happens automatically at a lifecycle event, Plugin = how the extensions are packaged and distributed - a skill decides how, MCP reaches outside, a hook enforces, a plugin distributes - and each attaches at a different point in the agent loop. A skill is a folder whose description controls discovery and whose body holds the procedure, model- or user-invoked, with the body loading only when the skill runs and side-effecting workflows usually requiring explicit invocation; a plugin is the packaging layer giving installation, versioning, namespacing, team reuse and distribution. (p30, p31, p33, p34, p35, p39)
- MCP (Model Context Protocol) connects the agent to external services through a standard protocol, giving capabilities that exist neither in the model nor in local files; a call is almost identical to a local tool (same name, description and typed schema, same call-and-return contract) because "it just runs in another process", and the protocol carries the call while the agent still decides whether to make it. It has three primitives - Tools, Resources, Prompts - is user-controlled for prompts, and needs least privilege, separated reads and writes, distrust of tool output as instructions, and vetting before installing. (p36, p37, p47, p49)

### Teaching points
- The pedagogical spine is the separation of "model proposes" from "harness executes" (p9): an agent is a loop plus a trust boundary, not a smarter completion.

- Memory is taught as an economic decision, not a feature: "Every memory creation is a decision about what gets re-read forever" (p16) and "every permanent token is rent" (p26).
- Inference: MCP architecture and gateways sit in an "OPTIONAL - extra reading, not required" block (p45-p53), signalling that the graded core is the harness, not the protocol.

## Lecture 3 - Agent From a User's Perspective II: Multi-agent and Best Practice
- **Source PDF**: `course/site/slides/3_agent_use_2.pdf` (slides: 72 pages, extracted from that file)

### Concepts
- Superpowers is a software-development plugin (obra/superpowers) installed with `/plugin install superpowers@claude-plugins-official`, running six stages - clarify the problem, approve a design, write a detailed plan, test-driven build, review and verify, finish or integrate the branch - and its defining claim is that two agents sharing the same model and the same tools behave differently because only the instructions differ; its architecture puts a plugin as the distribution container with skills and hooks supplying the behavior, the repository holds .claude-plugin/plugin.json, hooks/hooks.json with a session-start hook, skills/ and tests/, and it ships nine skills including using-superpowers, brainstorming, writing-plans, using-git-worktrees, test-driven-development, systematic-debugging, requesting-code-review, verification-before-completion and finishing-a-development-branch. (p5, p6, p7, p8)
- A SKILL.md has front matter (metadata: name, description) and a body (the procedure); the brainstorming skill's procedure is inspect, classify scope, clarify requirements, compare approaches, present a design, wait for user approval, invoke writing-plans, and a skill file can define six components: entry conditions, required actions, prohibited actions, human approval gates, verification requirements, next applicable skill. (p9, p10)
- Skills alone are not enough - availability does not guarantee the agent checks them - so a SessionStart hook with matcher "startup|clear|compact" guarantees deterministic timing, runs before the agent acts, and re-runs after clear and compaction; the session-start script locates the plugin, reads the bootstrap SKILL.md, escapes the Markdown for JSON and returns it as `additionalContext` for Claude Code to add to context. (p11, p12)
- Caveman is a second case study with five extension mechanisms plus a local proxy, installed via `claude plugin marketplace add JuliusBrussee/caveman` then `claude plugin install caveman@caveman`; it compresses because context fills up, every turn costs, and compaction loses detail - the worked example shrinks 786 lines of test output to "3 tests fail: ETIMEDOUT at client.ts:88" while the original stays available for retrieval. (p15, p16)
- Caveman compresses in two directions: the response skill changes how the model writes and the local proxy changes what it reads, reported as 65% fewer output tokens (though the skill itself adds input tokens, so whole-session savings are lower), through a seven-step flow ending with MCP retrieving the original on demand; its surfaces are a response skill preserving technical terms, commands, paths, code, errors, numbers, units and negation while removing filler, repetition, pleasantries and hedging, eight commands from /caveman to /caveman-help, SessionStart and UserPromptSubmit hooks that make a prompt-time choice persistent, and five MCP tools including caveman_compress (compress + recovery handle), caveman_retrieve (byte-exact original) and caveman_stats, packaged as a plugin. (p17, p18, p19, p20, p21, p22, p23, p25)
- The proxy is the only mechanism that can transparently rewrite what the model reads - hooks intercept requests but cannot rewrite the request to the LLM, so a proxy is required unless you write your own harness; the proxy sits between agent and model provider while MCP sits beside it, and it applies type-aware compression per content type (logs, code, diffs, JSON, search, HTML/text). (p24)
- Three axes of scaling: parallel agents (breadth - independent tasks each in an isolated working tree, buying wall-clock throughput not answer quality), subagents (breadth and depth - a bounded task in fresh context returning a summary, buying throughput and focus), and long-running agents (duration - a larger job carried across many steps, buying scope); agent teams and dynamic workflow combine them. (p27)
- Parallel agents by hand means one task per session in its own git worktree, a separate working directory and branch sharing the repository's history, and hand-run parallelism breaks down past a few sessions - you hold the plan, sessions cannot see each other, you reconcile the branches, and it does not repeat because nothing is written down to rerun. (p28, p29, p30)
- Subagents are a specialized assistant with its own context window, tools and permissions, used to preserve context, enforce constraints, reuse anywhere, parallelize (the slowest subtask sets the total time) and control cost by routing to a cheaper model such as Haiku; built-ins are Explore, Plan and General-purpose, a subagent is a Markdown file with YAML frontmatter whose body becomes the system prompt, nesting requires `Agent` in the tools list, up to 5 levels are allowed with 2 to 3 the sweet spot, and three invocation styles (natural language, @-mention, --agent flag) give increasing control. (p31, p32, p33, p34, p35, p36, p37)
- Agent teams are several Claude Code sessions working together - one lead, several teammates - for review, independent modules, debugging and cross-layer work; subagents report back to the caller while teammates share a task list and talk to each other, teams cost more tokens and are worth it only when the work needs discussion, and they are experimental and off by default. Dynamic workflow is a JavaScript script orchestrating many subagents in the background (entered by typing "ultracode" or running `/effort ultracode`), and the two long-running forms are `/goal`, which runs until a verifiable end state holds, and `/loop`, which re-runs a prompt on a schedule until you stop it. (p38, p39, p40, p41, p42, p43, p44, p45, p46)
- Programming 3.0 (the lecturer's own coinage, explicitly different from Andrej Karpathy's definition) expresses the goal rather than machine instructions or source language, trading higher productivity for more uncertainty; Software 3.0 is human language/context -> LLM -> action against Software 1.0 and 2.0, and knowing where to draw the boundary between them is an important engineering skill. Uncertainty is not new - Programming 2.0 already had 32-bit vs 64-bit architecture, endianness, concurrency, unreliable networks, compiler versions and dependency drift, solved with fixed-width types, cross-compilation, virtualization, a memory consistency model, idempotent APIs and comprehensive testing - and the best-practice groups are DEFINE (state assumptions up front; have the model confirm anything ambiguous before it executes), CONTROL (separate proposal from execution; manage context explicitly, owning memory, provenance and retrieval and expiring stale information; specify outcomes, not prompts) and VERIFY & GOVERN (tighten the generate-verify loop; measure one level deeper), under the rule "Do not expect the agent to be deterministic; make the surrounding system dependable" and "match autonomy to risk: the more autonomy the higher uncertainty and risk". (p52, p53, p54, p55, p56, p57, p58, p59)
- The field evidence contrasts conversational AI (the human is the executor) with agentic AI such as Codex (the human delegates, then reviews and integrates), and ends on a five-rung Delegation Ladder from Chatbot to Systematized workflows. (p61, p68)

## Lecture 4 - Agent Design I: context management and tool design
- **Source PDF**: `course/site/slides/4_agent_design_1.pdf` (slides: 56 pages, extracted from that file)

### Concepts
- The ReAct loop interleaves Thought (what do I know, what is missing, what next), Action (emit a structured call the environment can run) and Observation (the environment answers with facts); reason-only fails because nothing checks the reasoning and small errors compound into confident hallucination, and act-only fails because tool calls with no plan make the model repeat themselves. (p4)
- The reference implementation is a message-list loop - system and user messages, then for step in range(MAX_STEPS) call the model with tools, append the response, return the final answer if present, otherwise validate arguments, execute the tool and append a role "tool" message - and exceeding the step limit raises "Agent exceeded its step limit"; a harness designer's three jobs are to assemble the context, to validate the request, check permission and run it, and to optionally process the result and manage context, so that a coding agent has three components sharing one context window - model + agent loop, tools and guardrails, and state - meaning "an agent is a model plus a loop" and "tools set capability; guardrails keep it safe". (p5, p6, p7)
- Four ways to find code: glob and grep, which the agent loops over with nothing to build or keep in sync and which always reflect the live repo, at the cost of burning turns and context and missing paraphrase; semantic/structural search, embedding code chunks or using a file tree plus ranked symbols (Aider's repo map), which is fast at query time but costs building and re-syncing the index; extrinsic signals - evidence outside the source such as stack traces, failing tests and git history, the highest-precision signal when debugging, useful only when such a signal exists; and a language server (LSP), which queries the compiler's index for definitions, references, symbols and types and resolves imports, overloads and renames that grep only guesses at, at the cost of a live server per language and a slow cold start. (p10, p11, p12, p13)
- The comparison rule: "In practice - start with grep; reach for an index or LSP when names run out." (p14, p15)
- Four edit strategies: whole-file rewrite (no patch syntax to get wrong, but output scales with file size and untouched code can drift), unified diff/patch (compact and reviewable in the format humans and CI already use, but hunks fail when line numbers or context drift), search and replace (output proportional to the change, but fails on ambiguous, stale or whitespace-off anchors), and structured/AST edits (immune to formatting and cannot produce invalid syntax, but per-language tooling and a limited set of expressible edits). (p17, p18, p19, p20, p21)
- Shell execution is the most powerful and most dangerous tool - composition (one call can chain, filter, loop and retry), reach (filesystem, network, package managers, installed binaries), persistence (files and processes outlive the call), blast radius (whatever the shell can do, the agent can do) - and its design must settle failure signal, output, duration, budgets (when to stop retrying and hand back) and isolation (where the code runs and what it can reach). (p22, p23)
- Five more commonly used tools: browser and visual feedback, memory and notes (write findings to a file so plans survive compaction), asking the user (one cheap question beats a confident wrong patch), subagents and delegation, and web search and fetch. Tool design best practices: few orthogonal tools (overlapping tools make the model dither), purpose-built rather than generic (search_orders(customer_id) beats a raw run_sql tool), token-cheap output (truncate, paginate, summarize - tool design is context design), errors that teach (return the fix hint, not just "invalid argument"), and idempotent by default. (p24, p25)
- The engineering taxonomy has shifted: Prompt Engineering (2023-2024, "How should we instruct the model?") -> Context Engineering (2025-2026, "What should the model see?") -> Harness Engineering (2026, "How should the agent operate?") -> Goal Engineering (Now -> Next, "What counts as success?"), and the deck is explicit that "People love coining terms. I use them so you'll know what they mean when you encounter them, but that doesn't mean I agree or like them." Eight prompting techniques are surveyed in the same spirit - zero-shot, few-shot, role & persona, chain-of-thought, tree-of-thoughts, self-consistency, prompt chaining, meta prompting - each with a "use it when" and a "move on when" (5 samples at T = 0.7 voting 4/5 = 0.8 with a floor of 0.8 and 3/5 routed to a human; meta prompting turning 8/10 into 10/10 on an eval set), under four prompt-design rules: instruction, delimiter, data - in that order; start simple then iterate; partition into sections; be specific and concise; split big tasks into subtasks. (p28, p29, p30, p31, p32, p33, p34, p35, p36, p37, p38, p40)
- Context engineering is "the delicate art and science of filling the context window with just the right information for the next step" (Andrej Karpathy), and context is a finite resource on three axes: cost (every step re-sends the whole window), latency (bigger prompts take longer to prefill and decode) and attention (recall fades as the window fills; the middle gets missed, so more context is not better answers); both length and position cost accuracy, with accuracy decaying as input grows and depending on where in the window the answer sits. (p41, p42, p43)
- The illustrative token budget for one agent turn is system prompt ~2K, tool definitions ~6K, retrieved context ~25K, project environment ~8K, and message history (user + LLM + tool-call result) ~80K and growing; managing it takes four escalating stages - Admission (targeted retrieval, tool output shaping, truncation only when shaping cannot, isolation to a subagent), Offloading (progressive tool definition, tool search, tool output offload returning a handle, externalised task list, persistent memory), Transformation (deduplication, observation masking of tool results older than N steps, sliding window) and Compaction (rolling summary, or full summary at the limit, reserving headroom, preserving the system prefix, re-injecting critical facts, persisting key facts outside the window via auto memory) - moving from "preventive and lossless" to "lossy and irreversible". (p44, p45, p46, p47, p48, p49)
- Five ways context fails: Poisoning (a hallucination enters the window and is later cited as fact), Distraction (history grows until the agent imitates its own past actions), Confusion (irrelevant tools and documents steer the answer off course), Clash (new information contradicts old; both stay unresolved) and Drift (the real goal is buried and swapped for a nearby subgoal) - "Name the failure and the fix becomes obvious." (p50)
- The thesis: Agent = Model x Harness. Model capability sets the ceiling; the harness determines realized performance - and the evidence is that changing only the harness doubles accuracy, so "some apparent 'model failures' are actually context- and control-loop failures." (p51, p52)
