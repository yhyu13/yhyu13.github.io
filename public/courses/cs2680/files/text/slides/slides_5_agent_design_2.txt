1. Supervisor–worker
• One agent plans, delegates and integrates; workers see only their subtask
Supervisor
Researcher
Coder
Reviewer
Best when subtasks are independent and can run in parallel
Weakness: the supervisor bottlenecks: it re-reads every result and its context grows fastest.
Task: supervisor splits up front ·   Control: one supervisor ·   Comms: star, via supervisor

4. Blackboard and shared memory
• Agents coordinate through shared state instead of direct messages
• The workspace may be a database, vector store, filesystem, Git repo or task graph
Task: emerges from shared state ·   Control: none central ·   Comms: indirect, via workspace
Agents can join or leave without rewiring; the shared state is durable and inspectable
Challenges: consistency, concurrency control, provenance, versioning, garbage collection.
Git repository
task list, commits, history
Feature agent
Refactor agent
Test agent
Example: agents sharing a Git repo

• Agents propose and discuss, then a judge or vote resolves the disagreement
Judge

6. Market and auction
• Agents bid for announced tasks based on capability, cost and latency
• Heterogeneous agents differ in models, tools, machines, cost and expertise
“Who can run this training job?”
A100 node
$0.20 · ETA 3s
T4 node
$0.05 · ETA 10s
H100 node
$0.40 · ETA 1s
Job goes to A100 node
Example: GPU job router — cheapest bid under 5s wins
Task: announced, claimed by bid ·   Control: auctioneer clears ·   Comms: broadcast, bids back
Work lands on the cheapest capable agent with no central planner
Weakness: bids are self-reported, so an agent can win by overstating what it can do

7. Swarm
• No permanent coordinator, agents negotiate and exchange findings directly
• Needs protocols for discovery, addressing, synchronization, termination, trust
Picker 1
Picker 2
Picker 3
Picker 4
Example: warehouse robots negotiating who picks which order
No coordinator to bottleneck or fail; work continues as peers drop in and out
Weakness: communication complexity O(n²); conflict resolution are hard. Rarely used in products. 
Task: negotiated locally ·   Control: no permanent coordinator ·   Comms: all-to-all, O(n²)

Granularity tradeoff
Tasks too large
Little parallelism; the work stays 
sequential
Tasks too small
Scheduling and communication overhead 
dominates
Tmulti ≈ Tplanning + Tcritical path + Tcommunication + Tmerge

communication and integration costs.

Static versus dynamic decomposition
Static
Known before execution; predictable and 
easy to evaluate
Example: summarize each of five uploaded PDFs
Dynamic
Agents create new tasks in response to 
discoveries
Example: a dead link spawns a lookup task
Recursive
Workers may themselves delegate
Example: a review agent spins up one sub-
agent per subfield
Opportunistic
Idle agents claim newly available tasks
Example: an idle agent picks up the next 
unlabeled document
Decomposition needs spawning limits, budgets, depth limits and termination conditions
Without them, delegation explodes recursively.

Design principles 
1  Is multi-agent really necessary?
Single agent is sufficient, multiple agents 
often only adds overhead and complexity
2  Decide topology
reflect task dependencies, minimize 
communication
3  Identify information-loss points
treat aggregation nodes as places where 
detail drops
4  Identify failure-containment 
boundaries
Make sure the system does not stall
A dense mesh is rarely the best default. More communication can 
increase context pressure without increasing useful information.
